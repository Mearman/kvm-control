# Compatibility and verification

## Device profiles

The KVMD adapter provides `PiKvm` and `GlKvm` profiles. Its implementation follows selected upstream KVMD routes and response shapes; the upstream revisions inspected are linked in the module documentation in [`crates/kvm-kvmd/src/lib.rs`](crates/kvm-kvmd/src/lib.rs). A profile name is not a tested device or firmware matrix. No physical hardware was tested for this documentation, and the tests in this checkout do not establish real-device interoperability.

Capability discovery can return `Supported`, `Unsupported` or `Unknown`; unknown is not support. Snapshot and live-video capabilities remain `Unknown` until this connection has validated a JPEG from the respective operation, for live video possibly before any caller has read that frame; a failed operation does not establish that it is unsupported. HID discovery requires a successful HID response: a request failure makes `capabilities()` fail rather than returning unknown HID capabilities. A successful response can still leave keyboard or mouse capability unknown when the relevant state is absent or offline. Absolute mouse movement requires the reported absolute mouse mode. Control operations require the relevant capability to be confirmed and can return an unverified outcome even when accepted.

Status is typed: `status()` reads the info, HID, streamer, ATX, switch, GPIO and media state routes with GET requests only. Each subsystem and each observed state value is reported as `Supported` with its value, `Unsupported` or `Unknown`; identifiers such as switch port numbers, GPIO channels and image names, and composite parts such as ranges and resolutions, are plain values. Both inspected sources always serve the info, HID and streamer routes, so a 404 on any of them fails status as an HTTP 404. Another route that does not exist is unsupported once the info route has been read, and unknown otherwise. A route the session may not read, or one that fails (an HTTP error, `ok: false`, a missing result, malformed JSON, an oversized body, no complete response by the request's overall deadline, or a body that broke off), is unknown without discarding the others; PiKVM's info route runs the streamer twice per request to read its version and features, so it can be the slow one. When no route could be read, status fails: with an authentication error if any route was denied, otherwise with the info route's error, such as the HTTP 502 of a proxy whose daemon is stopped. Failing to establish a connection or TLS session within `Endpoint::timeout` fails status at once as a transport error, also when earlier routes were read, since the device can no longer be reached. Under `Endpoint::timeout` the connection (TCP and TLS) must be established within it and a whole request other than live video ends within twice it from sending, so a stalled handshake is told apart from a slow answer; a slow route on an already established connection is unknown only after twice the timeout, and a status read of seven routes can take up to seven such deadlines. A denied subsystem is unknown so that a partly permitted session keeps what it may read; because invalid or expired credentials can look the same when some route is readable without them, unknown from a denied route may mean the credentials are invalid or expired, and `check_auth` or a new login confirms it. A disabled ATX or media plugin reports placeholder values, so it is reported unsupported rather than read, and so is a switch with an empty port list, which PiKVM serves when no switch is attached or its units are not ready; as in capability discovery, a switch response without a port list is unknown, and GPIO with no channel configured is unsupported, but GPIO that lists only inputs is reported with them although its control, which only outputs accept, is unsupported. Placeholder state is unknown: GPIO channel state while the channel is offline or busy, keyboard LEDs while the keyboard is offline, the mouse mode while the HID reports itself offline (PiKVM's MCU HID reports absolute then; the OTG and Bluetooth plugins always report themselves online with their configured mode, which is kept; the CH9329 plugin reports its real online state as the integer `0` or `1`, which is read as a boolean, so its state is reported and its mode is hidden only while it is offline; capability discovery reads the mode independently), and the capture resolution while the source has no signal. A streamer started with uStreamer's `--fake-width` and `--fake-height` reports the configured size as the resolution while online, which the response does not distinguish ([`server.c`](https://github.com/pikvm/ustreamer/blob/11fd828ab00c01a39bd0843ef442ef0b6d3cac41/src/ustreamer/http/server.c)); the source trees at revisions P and G contain no use of those options, which does not cover a device's own configuration. Response shapes come from source revisions P and G below, linked from [`crates/kvm-kvmd/src/status.rs`](crates/kvm-kvmd/src/status.rs); whether a released firmware reports each field is unverified. In those revisions only PiKVM reports per-button ATX activity, only GLKVM reports a partition-backed media drive and the `h265`, `zero_delay` and `venc_mode` streamer features, and GLKVM returns a fixed switch `synced` flag, a fixed streamer version and a fixed platform type, which are therefore reported unknown for that profile. A remote media image's URL is not exposed, since it can embed credentials. The CLI, MCP server and terminal client escape control and bidirectional formatting characters in device text before showing it.

Cookie login supports a device approval flow. Cookies are accepted from login or approval responses but later cookie rotation and expiry updates are ignored. Firmware requiring rotation is therefore unsupported. On expiry or revocation, authenticate again; do not automatically replay uncertain input or control operations.

## Connection and video

The adapter requires HTTPS and rejects endpoint URLs containing credentials, query parameters or fragments. It does not follow redirects. A direct device origin and a reverse-proxy path prefix are both represented by the same endpoint configuration. A proxy must preserve the API routes and WebSocket upgrade as well as the separate MJPEG route. Live video opens a WebSocket stream lease and reads multipart JPEG from `streamer/stream`; it is not a WebRTC client. A device or proxy that does not expose those routes cannot provide this live stream through the adapter. The H.264 media WebSocket and Janus WebRTC transports the inspected PiKVM source offers, and GLKVM's Janus extra and adaptive WebRTC mode, are not implemented; the [video transport investigation](docs/video-transports.md) records how each is negotiated and how the adapter could select one.

## Terminal and platform

The terminal client needs an interactive terminal and a stream of decodable JPEG frames. Its image protocol and keyboard enhancement are detected by querying the terminal, with environment heuristics for a terminal that does not answer, and the image protocol can be selected explicitly; native image protocols need support from the terminal and, under tmux, externally enabled passthrough. Without terminal key-release events, input falls back to key taps. A capability reported as unknown or unsupported can prevent input forwarding. The MCP executable's inherited password pipe is implemented for Unix only; this is a prerequisite independent of whether another part of the workspace compiles on a platform.

## Evidence in the repository

Unit tests exercise capability handling, input behaviour, video parsing and terminal logic. Integration tests use synthetic devices, loopback HTTPS servers, generated test certificates and fake MCP devices, including protocol and shutdown cases. The command-line tests run the real `kvm-cli` binary against a synthetic authenticated HTTPS and WebSocket device, which grants a stream lease and serves several distinct valid JPEG frames, and check the newline-delimited JSON the `video` command emits and that the lease connection is released. The example in `examples/in-process` implements a synthetic device. These are useful contract and regression tests, not tests against a physical PiKVM, GLKVM, attached host, native terminal, proxy configuration or a particular firmware release. No hardware, credentials or live device were used to prepare this documentation.

## Hosted verification

Pull requests and pushes to `main` are checked by `.github/workflows/ci.yml` on GitHub-hosted runners. The `Checks` job runs on Ubuntu and macOS and covers formatting, Clippy with warnings denied, workspace tests with the lockfile enforced, the tests of the independent consumer in `examples/in-process`, and the release version stamping; further jobs test the release planning and recovery scripts and, on pull requests, that every commit is a Conventional Commit. The workflow configuration shows what is checked; whether a particular commit passed is shown only by the check results for that commit, so consult them rather than inferring it from this file. A passing check is a synthetic-device result and not a hardware compatibility result.

## Distribution

The same workflow builds the `kvm-cli`, `kvm-mcp` and `kvm-tui` binaries in release mode for 64-bit x86 and Arm Linux and macOS, each on a GitHub-hosted runner of that target. Every build is stamped with a version, packaged as one `.tar.gz` archive per target with a SHA-256 checksum file, unpacked and smoke-checked on the runner that built it: the archive must hold exactly those three binaries, `kvm-cli --version` must print `kvm-cli` and the stamped version, `kvm-cli` and `kvm-tui` must print their help, and `kvm-mcp` must reject a missing configuration with an error naming the unset `KVM_ENDPOINT`. On a pull request the build is stamped 0.0.0 and kept only as a workflow artefact.

On a push to `main`, releases are automatic and follow [Conventional Commits](https://www.conventionalcommits.org/): `.convco` defines which commit types change the version, and [convco](https://github.com/convco/convco) calculates the next version from the commits since the last release tag, with 0.1.0 as the first release. Below 1.0.0 a breaking change bumps the minor version and any other releasing commit, a feature included, the patch version, following Cargo's convention that a 0.x minor version is the breaking one. Once the checks pass, the workflow pushes the `vX.Y.Z` tag, creates a draft GitHub release with notes generated from those commits, uploads the archives and checksum files, downloads them again and compares each with its checksum and with the digest GitHub reports, and only then publishes the release. A final job downloads each published archive without authentication on a runner of its target, verifies its checksum and repeats the smoke checks. A run that stops after pushing a tag is resumed by the next run on `main`, which builds that tag's own commit and finishes its release before any later version; re-running a completed release verifies its published assets without replacing them. Release creation uses only the workflow's own token. Nothing is published to a package registry, and the archives are not signed or notarised.

The smoke checks run the binaries without a device, so a release shows that they start on each target, not that they work with any particular device. Do not assume a supported upgrade path or a stable API from a version number. Physical devices and firmware releases remain not independently tested; verify the exact target and device combination you intend to use.
